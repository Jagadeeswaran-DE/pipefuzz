Scenarios decide which difficult inputs to generate. Invariants decide what counts as a failure. Choose both explicitly so each run tests the properties your transformation is meant to preserve.

The five scenarios

Scenarios use small templates with compact values. They satisfy the required adversarial structure while respecting the configured minimum row counts. The maximum row count is a bound, not a promise to generate that many rows. A finite run explores a sample of possible cases; passing is not proof for every input.

NameGenerated caseUseful for
nullsSelects an eligible input and nullable column, creates at least one row, and sets that column to NULL in the first row. Other values in that selected row are non-null compact values.NULL propagation, missing-value handling, and transformations that assume values always exist.
duplicatesSelects an input that allows at least two rows and makes its first two records identical.Deduplication logic and checks that output keys stay unique when inputs repeat.
join_amplificationSelects a declared relationship, coordinates its join keys, creates at least one source row, and creates at least two identical matching target rows.Detecting measure inflation from duplicate dimension rows in an intended many-to-one join.
numeric_edgesSelects an eligible numeric column and puts an edge value in the first row. Other fields use type-appropriate default values.Zero, negative values, bounded extremes, and arithmetic assumptions.
determinismPopulates the first input that permits a row with compact non-null values. When deterministic_output is configured, runs the transformation twice using the same input DataFrames.Changes in returned values between repeated calls, such as unseeded randomness or a changing timestamp.

Inputs not selected by the scenario use their minimum number of rows filled with type-appropriate defaults: zero, an empty string, false, or a fixed UTC timestamp. Join cases use these defaults for non-key fields too, except that measures referenced by a matching no_join_amplification check are set to a positive unit. For decimals, that unit is 10−scale.

Scenario names go in the top-level list. This is a fragment to add to a configuration with eligible schemas and a relationship:

scenarios:
  - nulls
  - duplicates
  - join_amplification
  - numeric_edges
  - determinism

The configuration reference lists the required row limits and column types for each scenario. Non-join scenarios do not coordinate relationship keys across inputs.

Numeric edge values

The numeric scenario samples the following sets. Floating-point generation uses finite values; it does not generate NaN or infinity. Decimal edges are deliberately capped and do not cover every value representable by high-precision decimals.

TypeCandidate edge values
integer0, 1, −1, −2147483648, 2147483647
long0, 1, −1, −9223372036854775808, 9223372036854775807
float, double0.0, 1.0, −1.0, −1000000.0, 1000000.0
decimal(p,s)Unscaled values 0, 1, −1, −M, M, multiplied by 10−s, where M = min(10p − 1, 1000000).

When checks run

unique_key, no_unexpected_nulls, and no_join_amplification run for every generated case in every enabled scenario. deterministic_output runs only in the determinism scenario. Enabling that scenario alone does not add a comparison check; configure the invariant too.

Scenarios run in configuration order. When a case fails, Hypothesis attempts to shrink it within that scenario's strategy, and PipeFuzz reports the failure and stops the run. A report therefore does not mean that all later scenarios were exercised. A transformation exception also fails the run even if no invariant has been evaluated.

unique_key

Checks that each tuple of configured column values occurs at most once in the chosen dataset. For a compound key, it checks the combination, not each column separately. dataset can be an input name or output.

invariants:
  - type: unique_key
    dataset: output
    columns: [customer_id, order_date]

The column names in this fragment must exist in the returned DataFrame. Repeated tuples containing NULL count as duplicates; a single NULL key can pass. Repeated floating NaNs are normalized for duplicate detection. The check does not apply approximate numeric tolerances. Empty datasets pass.

For a non-null unique key, also add no_unexpected_nulls for the same columns. An input-level uniqueness check can intentionally fail the duplicates scenario: that scenario generates duplicate input records.

no_unexpected_nulls

Counts NULL values in every listed column. Any nonzero count fails the check and is included in the failure context.

invariants:
  - type: no_unexpected_nulls
    dataset: output
    columns: [total_amount]

This checks actual values, independently of the column's declared nullability. An empty string, zero, or floating NaN is not NULL. Empty datasets pass. Configure an input name as dataset to inspect generated inputs, or output to inspect the transformation result.

no_join_amplification

Checks a measure that the transformation is expected to conserve or reduce. It sums the absolute value of each non-null input measure and compares that total with the same calculation on the selected output column.

invariants:
  - type: no_join_amplification
    relationship: orders_customer
    input: orders
    input_column: amount
    output_column: total_amount
    rtol: 1.0e-9
    atol: 1.0e-12

This fragment uses the orders_customer relationship from the complete configuration. The input must be that relationship's from input, and its selected column must have a numeric schema type.

input_total  = sum(abs(value) for each non-NULL input value)
output_total = sum(abs(value) for each non-NULL output value)
tolerance    = atol + rtol * input_total

pass when output_total <= input_total + tolerance

For input values 100 and −100, the total is 200. Taking the absolute value after summing would give zero and is not the calculation used here. The check also catches amplification of negative values.

  • NULL values contribute nothing to either total. Empty inputs or outputs have a total of zero.
  • Non-finite floating-point values make this check fail. A missing output column or a value that cannot be interpreted numerically is a configuration error.
  • Totals use Decimal arithmetic; non-Decimal values are converted through their string representation.
  • The failure context includes the relationship, column names, both absolute totals, and the computed tolerance.

Choose a measure whose meaning fits the check. This compares whole-dataset totals. It does not inspect a query plan, prove join cardinality, check each key, or detect data loss. A reduction in output can pass. Legitimate transformations that increase a measure can fail. Use additional checks for other requirements.

deterministic_output

Calls the transformation twice for each determinism case and compares the materialized outputs. Both calls receive the same input DataFrames within the run's local Spark session.

scenarios: [determinism]
invariants:
  - type: deterministic_output
    rtol: 1.0e-9
    atol: 1.0e-12

Add the fragment above to an input configuration with at least one input that allows a row. Outputs are compared as unordered multisets: row order can change, but each row must have a matching counterpart and duplicate counts must match.

Part of the outputComparison rule
SchemaExact schema snapshot equality, including field order, types, nullability, and metadata.
Row countMust match exactly.
NULLMatches only NULL.
Finite floatsCompared using relative and absolute tolerances.
Floating NaN and infinityNaN matches NaN; infinities must have the same sign.
DecimalsBoth values must be Decimal values and compare equal; floating tolerances do not apply.
TimestampsNormalized to UTC. A timestamp without a timezone is treated as UTC.
Nested output valuesDictionaries and Spark rows compare recursively; lists and tuples compare in element order.
Other scalar valuesThe Python value type and value must match exactly.

The check concerns returned data from repeated calls. It does not test row ordering, persisted sinks, stateful pipeline idempotency, or results across different Spark sessions. Two matching calls do not establish determinism for every possible execution.

Two tolerance formulas

Both relevant invariant types default to rtol = 1e-9 and atol = 1e-12, but they use those numbers differently.

CheckAllowed difference
Join amplificationOutput total may exceed input total by at most atol + rtol × input_total. This is a one-sided upper bound.
Deterministic finite floatsabs(a − b) <= max(atol, rtol × max(abs(a), abs(b))), following math.isclose.

Use finite, nonnegative YAML numbers. For example, write 1.0e-9 rather than a quoted string. Setting both values to zero removes the numerical allowance in these comparisons.

Choosing a useful combination

Start with a property your transformation must preserve. For a customer join that must not inflate order amounts, declare the relationship, enable join_amplification, and add no_join_amplification. For a deduplication transformation, pair duplicates with an output unique_key check. For required output values, pair nulls with no_unexpected_nulls, ensuring the schema allows a meaningful NULL input.

Review the minimized records in a failure report to decide whether the transformation violates its contract or the configured property does not match its intended behavior. Continue with the broken and safe join examples, or return to the complete YAML reference.
