A many-to-one join can silently multiply a measure when the dimension contains repeated keys. These two repository examples use the same schema and assertion to make that failure visible.

The broken join

examples/broken_join/pipeline.py assumes that each customer key identifies one dimension row. Spark joins every matching row, so a duplicate customer repeats the order amount before the aggregation.

{{broken_pipeline}}

The function is ordinary PySpark code. PipeFuzz imports it, passes generated orders and customers DataFrames as keyword arguments, and materializes its result.

Declare the property

Both example directories contain the following configuration. The relationship connects orders to customers; join_amplification generates matching keys with duplicate rows on the customer side. The invariant compares the sum of absolute amount values with the sum of absolute total_amount values.

{{example_config}}

primary_key: [customer_id] describes the intended key. It does not suppress adversarial duplicate keys, and it does not independently assert output uniqueness. Add an explicit unique_key invariant when that is a property you need to test. See the configuration reference and scenario and invariant reference.

Run both versions

After the checkout installation, use your environment's pipefuzz executable. The following commands assume it is on PATH:

pipefuzz test examples/broken_join/pipeline.py::transform --config examples/broken_join/pipefuzz.yaml --max-examples 1 --seed 20260820
pipefuzz test examples/safe_join/pipeline.py::transform --config examples/safe_join/pipefuzz.yaml --max-examples 1 --seed 20260820

The broken example is expected to exit 1; the protected example is expected to exit 0. Run each command independently if your shell or CI runner stops at the first nonzero status.

Protect the measure before joining

examples/safe_join/pipeline.py reduces the customer dimension to one row per key before the join. The recorded audit passed the same configured check with one generated example.

{{safe_pipeline}}

Choose a survivor policy for real data. dropDuplicates(["customer_id"]) does not define which record survives when rows share a customer ID but disagree on country or other attributes. The selected row can be nondeterministic. A production transformation needs an explicit rule, such as a well-defined ordering with a tie-breaker, if those attributes matter.

The name “safe join” refers to this example's measure-amplification check. It does not certify dimension quality, attribute correctness, completeness, or every possible input. This invariant permits a lower output total, so dropped or unmatched orders need a separate assertion if losing them is unacceptable. See check semantics before applying the pattern.

Adapt the example

Keep the property specific to your pipeline. no_join_amplification is suitable when a measure should not increase across the transformation; a legitimate one-to-many expansion may need different assertions. Add the schemas and relationships you actually use, then select scenarios that challenge those assumptions. The CLI reproduction guidance explains how to retain the conditions of a discovered failure.
