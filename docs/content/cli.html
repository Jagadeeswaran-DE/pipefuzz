The CLI loads a Python transformation and a YAML contract, runs each configured scenario in local Spark, and reports either a passing check or a classified failure with a process exit code.

Usage

pipefuzz test <file-or-module>::<function> [options]
pipefuzz --help
pipefuzz --version
pipefuzz test --help

Run the executable installed into your Python environment. For commands that work without activating a virtual environment, see the quickstart.

Transformation targets

A target has exactly the form <file-or-module>::<function>. The final attribute must be callable; dotted function names such as Class.method are not accepted.

pipefuzz test examples/broken_join/pipeline.py::transform
pipefuzz test my_package.pipeline::transform --config path/to/pipefuzz.yaml

File paths can be absolute or relative to the current working directory. A reference ending in .py, containing a slash or backslash, or matching an existing path is handled as a file target. Otherwise PipeFuzz imports it as a Python module, which must be importable in the active environment.

The function must accept keyword arguments matching every configured input name and return one PySpark DataFrame. File targets can import sibling Python modules; PipeFuzz scopes those imports to the target's directory. Imports and the transformation run as ordinary Python in your process.

Configuration discovery

InvocationConfiguration used
Any target with --config PATHThat explicit path; a relative path is resolved from the current working directory.
File target without --configpipefuzz.yaml in the resolved Python file's parent directory.
Module target without --configpipefuzz.yaml in the current working directory.

There is no search through ancestor directories. Configuration is loaded before the transformation is imported. A missing or invalid configuration produces PIPEFUZZ_CONFIGURATION_ERROR. See the YAML reference for supported fields.

Choose scenarios and invariants in YAML; there are no CLI flags for selecting them. Scenarios execute in configuration order, and the run returns on its first discovered failure.

Exit codes and classifications

CodeReport classificationMeaning
0PASSEDNo configured invariant was violated by the executed generated cases.
1INVARIANT_VIOLATIONA generated case violated a configured invariant.
2PIPEFUZZ_CONFIGURATION_ERRORThe configuration, target, import, or callable signature is invalid; a configured invariant can also reveal a runtime contract error.
3TRANSFORMATION_EXCEPTIONThe user function, its output materialization, or return-type validation raised an exception.
4SPARK_ERRORLocal Spark startup or PipeFuzz-managed input materialization failed.
5PIPEFUZZ_INTERNAL_ERRORAn unexpected error crossed PipeFuzz's internal execution boundary.

Argument-parser failures, such as an unknown flag or invalid seed, also exit 2 but use the parser's usage/error text rather than a classified PipeFuzz report. A Spark AnalysisException raised by user transformation logic belongs to TRANSFORMATION_EXCEPTION; the exception's library name alone does not decide the classification.

Read a report

Run reports include the target, configured scenarios, generated-example count, Hypothesis version, and seed. A case failure adds the failing scenario, input schemas and minimized records, reason, and available invariant context. Early configuration failures can occur before a run exists and therefore do not have generated-case or reproduction details.

PipeFuzz writes passing reports to standard output and failing reports to standard error. Spark diagnostics may also appear in the terminal. Use the process exit status and classification to interpret the result; a warning line alone does not establish failure.

Reports intentionally display generated records and project schema names. Take that into account when retaining or sharing terminal logs. The example failure explains how a minimized case connects to the observed measure.

Reproduce a failure

pipefuzz test examples/broken_join/pipeline.py::transform --config examples/broken_join/pipefuzz.yaml --max-examples 1 --seed 20260820

Use the Reproduce command printed by the failing run. It includes the target, resolved configuration path, example limit, and seed; arguments use platform-appropriate quoting. Replace the executable with your virtual environment's path if needed.

Keep the same transformation code, configuration contents and scenario order, target, working directory, and example limit. Preserve the PipeFuzz, Hypothesis, PySpark, Python, and Java versions for comparable results. A seed controls generation; it cannot stabilize a transformation that depends on time, external state, randomness, or nondeterministic Spark behavior.

The report retains the original target text and an absolute configuration path. If you move the checkout or run on another machine, update those paths without changing the tested code or configuration. Changing Hypothesis or PipeFuzz versions can change generated values or shrinking behavior even with the same seed.

Execution scope

One local Spark session is reused across a CLI run. Generated inputs and transformation outputs are materialized locally, and output collection can exceed the input size. Keep this workflow focused on small logical tests. The architecture guide describes the runtime, and the checks reference explains what each passing result establishes.
