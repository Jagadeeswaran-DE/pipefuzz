PipeFuzz is a small local test runner, not a query analyzer or a production execution platform. This page connects the user-facing behavior to the code and explains where its guarantees stop.

The execution lifecycle

  1. Validate the configuration and target. Parse YAML v1, resolve the Python function, and check that it can receive the configured input names as keyword arguments.
  2. Start one local SparkSession. The CLI uses local[2], UTC session time, two shuffle partitions, a disabled Spark UI, and loopback driver networking.
  3. Generate Python records. Hypothesis explores compact schema-valid values within each enabled scenario. These records become actual DataFrames using explicit Spark schemas.
  4. Execute and materialize. Call the user transformation and collect the input and output DataFrames into driver-side snapshots. Collection forces Spark's lazy work to execute.
  5. Evaluate invariants. Pure Python checks inspect the snapshots. The determinism scenario calls the transformation again using the same equivalent input DataFrames and compares collected results.
  6. Shrink and report. Hypothesis reduces a failing invariant example within the strategy. The report includes generated records, schema, scenario, context, and reproduction details.
  7. Stop Spark. The CLI-owned session is stopped in a finally block.
Small inputs do not guarantee small outputs. A transformation can expand a few records dramatically. There is no enforced output-row cap, and collection can exhaust driver memory.

Privacy and trust boundaries

PipeFuzz itself runs locally, has no telemetry, does not upload code or data, and needs no API key or external AI service. Its datasets are generated; it does not need access to your production tables.

Your transformation is arbitrary Python. It can read files, make network calls, or write data, and PipeFuzz does not sandbox it. Only run code you trust, and avoid production credentials or side effects in test targets.

Failure reports print generated records and configured schema and column names. Those logs can expose sensitive project metadata even when the records are synthetic. Review logs before sharing them. This documentation website also uses no analytics or third-party fonts.

The v0.1 boundary

  • Only PySpark DataFrame transformations are supported. No SQL parser, dbt, Pandas, Polars, cloud execution, streaming, or persisted-sink testing.
  • Input schema types are the primitives in the configuration reference. Nested input schemas are not supported.
  • Relationships and invariants are explicit. PipeFuzz does not infer business semantics from Python or Spark query plans.
  • Generated collections use the smallest valid row count needed by a scenario, rather than exploring every size up to rows.max.
  • Determinism checks observed transformation output, not pipeline idempotency or external state. Two matching executions cannot prove the absence of nondeterminism.
  • Order-independent comparison retains duplicate multiplicities and requires equal schemas; it is designed for small snapshots, not large dataset reconciliation.
  • Measure amplification is only meaningful where the measure should be conserved. Filtering and reductions can pass; conservation in both directions is not asserted.

Verification, not a release promise

The recorded local audit on September 29, 2026 observed 49 passing tests on Windows with Python 3.13 and Java 17, built and installed a wheel, and ran both example CLIs. A subsequent hosted CI run for the initial commit completed successfully; its workflow covers Python 3.10 and 3.13 on Ubuntu. Python 3.11/3.12 and macOS were not separately verified in those runs.

The release audit is a historical record from before the initial commit and hosted CI. Its then-pending commit/CI statements describe that earlier point in time; publishing this documentation does not create a package release or a new audit verdict.

Contributing and the next milestone

From a development checkout, install with python -m pip install -e ".[dev]". Run unit tests without starting Spark, then the real-Spark integration suite with Java available:

python -m pytest tests/unit
python -m pytest tests/integration
python -m build

Keep reproductions small, add a regression for verified defects, and maintain the distinction between pipeline violations and runner errors. See contribution guidance, security guidance, and the code of conduct.

Carefully scoped SQL transformation support is the recommended v0.2 milestone, not an implemented v0.1 feature. The project is licensed under Apache License 2.0.
