Describe the inputs your transformation accepts, the difficult cases to generate, and the properties that must hold. PipeFuzz reads these settings from a YAML version 1 file.

A complete configuration

This configuration exercises all five scenarios and all four invariant types. It expects a transformation with orders and customers arguments that returns country and total_amount columns. The configuration is valid; whether it passes depends on the transformation. For a ready-to-run pair of transformations, see the join examples.

version: 1
inputs:
  orders:
    schema:
      - {name: customer_id, type: integer, nullable: false}
      - {name: amount, type: double, nullable: true}
    rows: {min: 1, max: 4}
  customers:
    schema:
      - {name: customer_id, type: integer, nullable: false}
      - {name: country, type: string, nullable: false}
    primary_key: [customer_id]
    rows: {min: 1, max: 4}

relationships:
  - name: orders_customer
    from: {input: orders, columns: [customer_id]}
    to: {input: customers, columns: [customer_id]}
    cardinality: many_to_one

scenarios:
  - nulls
  - duplicates
  - join_amplification
  - numeric_edges
  - determinism

invariants:
  - type: unique_key
    dataset: output
    columns: [country]
  - type: no_unexpected_nulls
    dataset: output
    columns: [total_amount]
  - type: no_join_amplification
    relationship: orders_customer
    input: orders
    input_column: amount
    output_column: total_amount
    rtol: 1.0e-9
    atol: 1.0e-12
  - type: deterministic_output
    rtol: 1.0e-9
    atol: 1.0e-12

Top-level fields

FieldRequired / defaultMeaning
versionRequired: 1The configuration format version.
inputsRequiredA nonempty mapping of input names to input definitions. Each name becomes a keyword argument to the transformation.
relationshipsDefault: []A list of declared many-to-one joins.
scenariosRequiredA nonempty list of supported scenario names, with no duplicates. Scenarios run in the listed order.
invariantsRequiredA nonempty list of checks. More than one check of the same type is allowed.

Unknown field names are rejected. The target function, seed, verbosity, and example budget are CLI options, not YAML fields.

Input definitions

Give every input a nonempty name matching a transformation parameter. Each input accepts exactly these fields:

FieldRequired / defaultRules
schemaRequiredA nonempty list of column definitions. Column names must be unique within the input.
primary_keyOptional; omitted means no declared keyWhen present, a nonempty list of distinct column names from this input's schema.
rows.min0An integer, not a boolean.
rows.max4An integer, not a boolean. Together the limits must satisfy 0 <= min <= max <= 20.

The rows mapping itself is optional. Scenarios use the smallest row count needed for their structure or the configured minimum, whichever is larger. Increasing max permits a scenario to run; it does not make PipeFuzz sweep every row count up to that limit. Unselected inputs can be empty when their minimum is zero.

A declared key is not a check. primary_key records intent and validates the column names. It does not enforce uniqueness, exclude NULLs, or add an invariant. Use unique_key and, when needed, no_unexpected_nulls to assert those properties. Adversarial scenarios can deliberately repeat declared keys.

Columns and supported types

Every schema entry must provide a nonempty name, a string type, and a boolean nullable. None of these fields has a default. Write unquoted true or false for nullability.

schema:
  - name: amount
    type: "decimal(12,2)"
    nullable: false
  - name: recorded_at
    type: timestamp
    nullable: true

Decimal precision must be from 1 to 38, and scale must be from 0 to precision. Quote decimal types in inline YAML mappings because the type contains a comma. Type names are normalized to lowercase, with surrounding whitespace and ordinary spaces removed. Aliases such as int, and input types such as dates, arrays, maps, or structs, are not supported in version 1.

nullable: false controls the generated input schema and values. It does not make a promise about the transformation's output. Add an output invariant if the result must contain no NULLs.

Relationships

A relationship describes the intended direction of a join: from is the many side, such as orders, and to is the one side, such as customers. The join scenario deliberately creates duplicate matching rows on the one side.

relationships:
  - name: orders_customer
    from:
      input: orders
      columns: [customer_id]
    to:
      input: customers
      columns: [customer_id]
    cardinality: many_to_one
  • name, from, to, and cardinality are required. Relationship names must be nonempty and unique.
  • Each endpoint requires an existing input and a nonempty columns list of distinct names in that input's schema.
  • The endpoints must name different inputs and have the same number of columns. Composite keys match by position; each paired column must have the same normalized type.
  • many_to_one is the only supported cardinality. Declaring a relationship does not automatically check key uniqueness or referential integrity.

Scenario settings

Choose at least one of the following names. These requirements are checked when the configuration loads; there are no additional per-scenario YAML options. See how scenarios generate data for their exact behavior.

ScenarioConfiguration requirement
nullsAt least one nullable column on an input whose rows.max is at least 1.
duplicatesAt least one input whose rows.max is at least 2.
join_amplificationAt least one relationship. For every declared relationship, the from input must allow at least 1 row and the to input must allow at least 2.
numeric_edgesAt least one numeric column on an input whose rows.max is at least 1.
determinismAt least one input whose rows.max is at least 1.

Invariant settings

Every invariant requires a type. The table lists the fields used by each type. For dataset, use an input name or the special name output for the returned DataFrame. Prefer another name for an input so that it does not conflict with output.

TypeRequired fieldsAdditional rules
unique_keydataset, columnsColumns form the complete key tuple. The list must be nonempty and contain distinct names.
no_unexpected_nullsdataset, columnsEvery listed column must have no NULL values. The list must be nonempty and contain distinct names.
no_join_amplificationrelationship, input, input_column, output_columnThe relationship must exist. input must equal its from.input, and input_column must be a numeric column in that input. Column references are individual names, not expressions.
deterministic_outputNo fields beyond typeThe determinism scenario must be enabled.

Input column references are checked while loading YAML. Output column references are checked after the transformation produces a DataFrame; an absent column is a configuration error. Output schemas are not declared in this format.

The parser recognizes type, dataset, columns, relationship, input, input_column, output_column, rtol, and atol within invariant definitions. Use the fields for the selected type: recognized fields belonging to another type may be ignored.

Tolerance defaults

Each invariant accepts optional rtol and atol, defaulting to 1.0e-9 and 1.0e-12. Values must be finite, nonnegative numbers, not strings or booleans. These options affect only no_join_amplification and floating-point comparisons in deterministic_output; key and NULL checks do not use them.

The formulas differ by check. Join amplification allows atol + rtol × input_absolute_total. Determinism uses Python's math.isclose for floats. See the formulas and value comparison rules before changing these settings.

Common configuration errors

  • A missing nullable, empty schema, unknown type, or unsupported field name.
  • A list supplied where a mapping is expected, or a mapping supplied where a list is expected.
  • A misspelled input, relationship, or column reference.
  • Row bounds that cannot accommodate a selected scenario.
  • deterministic_output configured without the determinism scenario.
